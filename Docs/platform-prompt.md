## 2. 🗂️ ข้อมูลตั้งต้น (Seed Data) — จาก WORKING_PROCESS.md

ระบบต้องมี seed script ที่สร้างข้อมูลชุดนี้ได้ทันทีหลังติดตั้ง **โดยอ่านจากไฟล์ข้อมูล (JSON/YAML) ไม่ใช่ฮาร์ดโค้ดใน component**

### 2.1 โปรเจกต์

| ฟิลด์ | ค่า |
|---|---|
| ชื่อ | CN360 Robot Rescue VR |
| คำอธิบาย | หุ่นยนต์สำรวจพื้นที่แคบ ควบคุมผ่าน PICO 4 ด้วยเว็บแอป (WebXR) ผ่าน Raspberry Pi และ ESP32 |
| เจ้าของโปรเจกต์ | แฟน |
| สถานะ | IN PROGRESS |
| วันเริ่ม / deadline | ให้ Project Owner กรอกตอนติดตั้ง (ใน WORKING_PROCESS ยังไม่มีวันที่) |

### 2.2 สมาชิก

| ชื่อ | บทบาทในระบบ | ตำแหน่ง | รับผิดชอบ |
|---|---|---|---|
| **แฟน** | PROJECT OWNER (+ ADMIN) | Leader + UX/UI | ภาพรวมโปรเจกต์, `Docs/protocol.md`, หน้าเว็บผู้ควบคุม, HUD, WebXR, จัดซื้อ |
| **โฟล์ค** | MEMBER | Raspberry Pi — Software | server บน Pi, `protocol.py`, failsafe ฝั่ง Pi, โหมด `--mock` |
| **นัท** | MEMBER | Raspberry Pi — System & Hardware | ติดตั้ง OS, กล้อง, สาย UART, ระบบไฟของ Pi, systemd, ROS 2 |
| **เม่น** | MEMBER | ESP32 | firmware มอเตอร์, servo, LED, watchdog, วงจรไฟมอเตอร์ |
| **สกาย** | MEMBER | Network | WebSocket, HTTPS, Wi-Fi AP, WebRTC/MediaMTX, วัด latency |

> ⚠️ **ห้ามฮาร์ดโค้ดอีเมล** ให้ seed เป็นค่าว่างหรือ placeholder แล้วให้ Project Owner กรอกอีเมลจริงในหน้า Team ก่อนเปิดใช้การแจ้งเตือน

### 2.3 Milestone

ระบบต้องมีเอนทิตี **Milestone** (เพิ่มจากสเปกทั่วไป เพราะทีมนี้ทำงานเป็น milestone)

| Milestone | เกณฑ์ผ่าน |
|---|---|
| **M1** | โครงสร้าง `WebApp/` พร้อม, `Docs/protocol.md` ทุกคน approve |
| **M2** | เว็บบน PC + server `--mock` รับคำสั่งถูกต้อง, failsafe ทำงาน |
| **M2.5** | เปิดเว็บผ่าน HTTPS บน PICO เข้า VR ได้ หันหัวแล้วค่า HEAD เปลี่ยน |
| **M3** | หัน PICO แล้ว servo หันตาม, joystick ขับมอเตอร์ได้, LED หรี่ได้ |
| **M4** | เห็นภาพกล้องหุ่นใน PICO แบบ real-time |
| **M5** | ทดสอบภาคสนามครบระบบ |

ความคืบหน้าของ milestone = สัดส่วนงานที่ DONE ในนั้น และแสดงบน Dashboard เป็น timeline แนวนอน

### 2.4 งาน (Tasks)

นำ **ทุกแถว** ในตาราง "Process รายคน" (หัวข้อ 3.1–3.5 ของ WORKING_PROCESS.md) มาสร้างเป็น Task โดย map ฟิลด์ดังนี้

| คอลัมน์ใน WORKING_PROCESS | ฟิลด์ใน Task |
|---|---|
| ชื่อคน (หัวข้อ 3.x) | Owner |
| งาน | Title + Description |
| ไฟล์ / ผลลัพธ์ | Deliverables |
| ขึ้นกับใคร | **Dependencies** (ลิงก์ไปยังงานของคนนั้น) + Collaborators |
| เสร็จเมื่อ | **Acceptance Criteria** (แสดงในหน้า Task และในฟอร์มส่งงาน) |
| **M1–M5** ในคอลัมน์ "เสร็จเมื่อ" หรือตารางหัวข้อ 5 | Milestone |

ตัวอย่างงานที่ระบบต้องสร้างได้:

```text
งาน:        endpoint /ws รับข้อความ → protocol.py → log
เจ้าของ:     โฟล์ค
Milestone:  M2
ไฟล์:        Robot/RaspberryPi/code.py
รอใคร:      —
เสร็จเมื่อ:   ws_client.py ของสกายยิง 1,000 ข้อความแล้วไม่มี error
ผู้ตรวจ:     นัท
```

งาน **Integration I-1 ถึง I-8** (หัวข้อ 4) ให้สร้างเป็น Task ที่มี **เจ้าของหลายคน** ตามคอลัมน์ "คนที่ต้องอยู่" และต้องพึ่งงานของทุกคนในขั้นนั้น ตัวอย่างเช่น I-6 ต้องผ่าน checklist ความปลอดภัยก่อนจึงจะส่งงานได้

## 3. 🔄 Workflow ของงาน

```text
  TODO
   ↓
  IN PROGRESS
   ↓
  SUBMITTED
   ↓
  IN REVIEW
   ↓

 │             │
```

## 10. 📧 การแจ้งเตือนทางอีเมล

**แจ้งเฉพาะคนที่เกี่ยวข้อง ห้ามส่งหาทั้งทีม**

| เหตุการณ์ | แจ้งใคร |
|---|---|
| ได้รับมอบหมายงาน | เจ้าของงานคนใหม่ |
| เปลี่ยน deadline | เจ้าของ + ผู้ร่วมงาน |
| ส่งงาน | ผู้ตรวจ |
| เริ่มตรวจ | เจ้าของ (ถ้าเปิดตั้งค่าไว้) |
| สั่งแก้ | เจ้าของ |
| อนุมัติ | เจ้าของ |
| **งานที่รออยู่เสร็จแล้ว** | เจ้าของงานที่ dependency เพิ่งปลดล็อก |
| คอมเมนต์ / @mention | คนที่ถูก mention |
| ใกล้ deadline (เช่น 2 วันก่อน) | เจ้าของ |
| เลย deadline | เจ้าของ + Project Owner (แฟน) |
| แก้ไขฟิลด์สำคัญ | ผู้ร่วมงานที่เกี่ยวข้อง |

ตัวอย่างอีเมล:

```text
[CN360]

🔁 งานของคุณต้องแก้ไข

งาน "Server: endpoint /ws"
ผู้ตรวจ: นัท

สิ่งที่ต้องแก้:
• แก้ failsafe ตอน WebSocket หลุด
• เพิ่ม test กรณีปิดแท็บ

Deadline: 6 ตุลาคม 2026

[ ดูงาน ]
```

- ใช้ transactional email provider ที่เชื่อถือได้ (เช่น Resend หรือ Postmark)
- **ส่งจาก server เท่านั้น** ห้าม API key หลุดไปฝั่ง client
- ส่งผ่าน background job / outbox เพื่อไม่ให้ request ช้า และกันการส่งซ้ำ
- ทุกอีเมลต้องมีลิงก์ตรงไปยังงานนั้น
- รองรับข้อความภาษาไทยและวันที่แบบไทย (เช่น "6 ตุลาคม 2026")

## 21. 🎨 UI / UX และฟอนต์ภาษาไทย

### ภาษาและฟอนต์

- **UI ภาษาไทยเป็นหลัก** ชื่อสถานะในระบบเป็นภาษาอังกฤษ แต่ป้ายบนหน้าจอเป็นภาษาไทย เช่น `IN REVIEW` → "รอตรวจ" และ `REWORK` → "ต้องแก้"
- ฟอนต์หลัก: **IBM Plex Sans Thai** (หัวข้อ + เนื้อหา) จาก Google Fonts
  - ทางเลือก: **Anuphan** หรือ **Noto Sans Thai**
  - ตัวเลข/สถิติ: ใช้ `font-variant-numeric: tabular-nums` เพื่อให้ตัวเลขเรียงตรงกัน
  - โค้ด/ชื่อไฟล์: **IBM Plex Mono**
- ตั้ง `line-height` ของภาษาไทยอย่างน้อย **1.6** เพื่อไม่ให้สระบน/ล่างและวรรณยุกต์ชนกัน
- ห้ามใช้ตัวพิมพ์ใหญ่แบบ `text-transform: uppercase` กับข้อความไทย
- วันที่แบบไทย ปี ค.ศ. (เช่น "6 ต.ค. 2026") ใช้ `Intl.DateTimeFormat('th-TH-u-ca-gregory')`
- เวลาแบบสัมพัทธ์เป็นไทย ("2 นาทีที่แล้ว") ด้วย `Intl.RelativeTimeFormat('th')`

### แนวทางการออกแบบ

**ต้องเป็น:** สะอาด · ดูพรีเมียม · ดูมืออาชีพ · เร็ว · ข้อมูลแน่นแต่ไม่รก · ลำดับความสำคัญชัด · ระยะห่างดี · สถานะชัด · interaction ลื่น · responsive · accessible · มี dark mode

**ห้าม:** หน้าตาแบบ Bootstrap สำเร็จรูป · gradient มากเกินไป · glassmorphism มากเกินไป · พื้นที่ว่างใหญ่ไม่มีประโยชน์ · animation สุ่ม · ของตกแต่งที่ไม่จำเป็น · dashboard ที่ยัดข้อมูลเกิน

**สีของสถานะ** (ใช้เหมือนกันทั้งระบบ):
TODO = เทา · IN PROGRESS = น้ำเงิน · IN REVIEW = ม่วง · REWORK = ส้ม · DONE = เขียว · เลยกำหนด = แดง

# CN360 Command Protocol v1

> สถานะ: **ร่าง รอทุกคนในทีมอนุมัติ** (`WORKING_PROCESS.md` §2.1)
> โค้ดที่ใช้จริง: `UI/src/services/protocol.ts` — ฝั่งหุ่นต้องรับบรรทัดที่ไฟล์นี้สร้างได้ทุกบรรทัด

## ข้อความ

```
DRIVE,<seq>,<linear -1..1>,<angular -1..1>,<speed_mode 1|2>    browser → Pi
HEAD,<seq>,<yaw deg>,<pitch deg>,<roll deg>                     browser → Pi
LIGHT,<seq>,<level 0..100>                                      browser → Pi   (0 = ปิด)
STATUS,<seq>,<battery_v>,<ack_seq>                              Pi → browser, 1 Hz
HELLO,<seq>,<mock|hardware>,<server_version>                    Pi → browser, ครั้งเดียวตอนเชื่อมต่อ (v1.1, เสนอ)
```

- ASCII คั่นด้วย comma ใช้ `.` เป็นจุดทศนิยม 1 ข้อความต่อ 1 WebSocket frame
- `DRIVE` ทศนิยม 2 ตำแหน่ง, `HEAD` 1 ตำแหน่ง, `LIGHT` เป็นจำนวนเต็ม
- บรรทัดที่ผิดรูปแบบ (จำนวนฟิลด์ผิด, ไม่ใช่ตัวเลข, ชนิดไม่รู้จัก) ให้ทิ้งและนับ ห้ามทำให้ระบบล่ม
- `seq`: ทิ้งคำสั่งที่ `seq` ≤ ค่าล่าสุดที่รับแล้ว รีเซ็ตเมื่อ operator คนใหม่เชื่อมต่อ
- `ack_seq` = seq ของคำสั่งล่าสุดที่ประมวลผลแล้ว (ไม่ได้ยืนยันว่าอุปกรณ์ขยับจริง)
- ฝั่งหุ่นต้อง clamp ทุกค่าเองด้วย

## LIGHT

| ฟิลด์ | ค่า | ความหมาย |
|---|---|---|
| `level` | จำนวนเต็ม 0..100 | 0 = ปิด, 1..100 = ระดับแสงเป็น % |

- UI มีปุ่มเปิด/ปิดกับแถบระดับแสง กดปิดจะส่ง `0` กดเปิดจะส่งระดับที่จำไว้
- UI ส่ง `LIGHT` เฉพาะหลัง operator เปลี่ยนค่าไฟ แล้วส่งซ้ำทุก 1 วินาที
- ฮาร์ดแวร์ปัจจุบัน (LED ACT บน Raspberry Pi) หรี่ไม่ได้: ระดับใดๆ ที่มากกว่า 0 = ติด

### เปลี่ยนจากร่างเดิม (`plan.md` Phase 1)

| เดิม | ใหม่ |
|---|---|
| `LIGHT,<seq>,<brightness 0..100>,<vision_mode 0\|1>` | `LIGHT,<seq>,<level 0..100>` |

ตัด `vision_mode` (โหมด IR / night) ออก เพราะหุ่นไม่มี IR LED หุ่นที่ยังรอ 2 ฟิลด์จะทิ้งบรรทัดใหม่ในฐานะบรรทัดผิดรูปแบบ
